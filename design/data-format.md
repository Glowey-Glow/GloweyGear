# Data format: stat weights (`Data\Weights.lua`)

Status: stage 1 contract between the engine (`Stats.lua`, `Score.lua`, `Spec.lua`) and the weights data. The engine is tested against exactly this shape (`Tools\tests\`), so a file that follows this page loads without code changes.

Short path names used for references:

- `DOC:` = `...\scratchpad\wow-ui-source\Interface\AddOns\Blizzard_APIDocumentationGenerated\` (the client's generated API docs)
- `FX:` = `...\scratchpad\wow-ui-source\Interface\AddOns\` (the client's own UI source, branch forever, commit 3d8abb1)
- `GAME:` = the installed game's own data files, read with `Tools\client_facts.py`; what it read is kept in `Tools\tests\fixtures\`

**What sections 2 and 3 rest on, and what they do not.** The stat names and the rating figures are facts read from the client itself (section 3.0). An earlier draft of this page and of `Stats.lua` was built another way: the stat names and rating figures were taken from the tables of two other addons that run on this client (Polestar, GPL-3, and Forever Leveling BiS, All Rights Reserved), and this page cited them line by line. That was wrong for an All Rights Reserved plugin and is gone: the tables were rebuilt from the client's data on 2026-11-20, in a structure of their own, and no table, order or comment of either addon is in the plugin. Where the rebuilt tables differ from the first draft, the client's data decided (section 3.8 lists the differences).

## 1. The file

`Data\Weights.lua` is a pure table: no functions, no `if`, no loops, no reads of the game. It can be regenerated by a script at any time. It sets one field on the addon namespace:

```lua
local _, ns = ...

ns.WeightData = {
	format = 1,                       -- bump only when this page changes shape

	WARRIOR = {                       -- key: the class file token, UnitClass's 2nd return
		default = "ARMS",             -- spec used while no talent point is spent (see 4.3)
		order = { "ARMS", "FURY", "PROTECTION" },   -- every selectable spec, in picker order
		specs = {
			ARMS = {
				tab = 1,              -- talent tree position, 1..3, left to right (see 4)
				role = "melee",       -- "melee" | "ranged" | "caster" | "healer" | "tank"
				source = "wowsims",   -- "wowsims" | "authored"
				sourcePath = "ui/specs/warrior/dps/presets.ts",   -- required when source = "wowsims"
				sourceCommit = "0123abc",                    -- required when source = "wowsims"
				confidence = "medium",                       -- "low" | "medium" | "high"
				note = "Max-level preset; leveling brackets authored.",  -- optional, English, never shown to players
				weights = {           -- value of ONE unit of each stat at max level (see 2 and 3)
					STR = 1.0, AGI = 0.6, STA = 0.1, AP = 0.45,
					CRIT = 14, HIT = 12, MH_DPS = 6.5, OH_DPS = 2.4, ARMOR = 0.01,
				},
				brackets = {          -- optional; see 5
					{ upTo = 19, weights = { HIT = 2, CRIT = 4, STA = 0.8 } },
					{ upTo = 39, weights = { HIT = 4, CRIT = 8, STA = 0.6 } },
					{ upTo = 59, weights = { HIT = 8, STA = 0.3 } },
				},
			},
			FURY = { ... },
			PROTECTION = { ... },
		},
	},

	PALADIN = { ... }, HUNTER = { ... }, ROGUE = { ... }, PRIEST = { ... },
	SHAMAN = { ... }, MAGE = { ... }, WARLOCK = { ... }, DRUID = { ... },
}
```

(The numbers above are made-up placeholders that only show the shape.)

Rules the loader checks (`ns.Spec.Validate`; a spec that breaks one is skipped with one debug line, the rest still load):

1. Class keys are exactly the nine tokens `WARRIOR PALADIN HUNTER ROGUE PRIEST SHAMAN MAGE WARLOCK DRUID` (the nine classes the client's talent UI knows: `FX:Blizzard_PlayerSpells\Camelot\ClassTalents\Blizzard_ClassTalentUtil.lua:1-11`). A missing class is allowed (the plugin then says it has no weights for the class and stays quiet).
2. Spec keys are upper-case ASCII words with `_` (`[A-Z_]+`), unique inside the class. They are saved in the player's settings, so never rename one after release.
3. Every key in `order` exists in `specs`. A spec that is in `specs` but not in `order` is ignored. `default` is in `order`.
4. `tab` is 1, 2 or 3. Several specs may share a tab (variants, see 4.4); the first one in `order` with that tab and without `manual = true` is the one Auto picks. A `manual` spec may be the class `default` (the shipped data does this with a `LEVELING` profile per class): it is then what Auto gives while no talent point is spent, and the first point spent hands over to the tree's own spec. Tested in `Tools\tests\test_spec.lua` and against the real file in `test_data.lua`.
5. `weights` holds only keys from the list in section 2, each a finite number. Negative values are allowed (a stat that hurts). A key left out is worth 0: **the engine derives nothing in stage 1** (no "health from Stamina", no "ranged from melee DPS"); write every value you want counted.
6. `source` and `confidence` are required. `sourcePath` and `sourceCommit` are required for `"wowsims"` and absent for `"authored"`. A spec seeded from wowsims and then hand-changed stays `"wowsims"` and says what changed in `note`.

Optional per-spec fields the engine already reads: `manual = true` (never picked by Auto), `brackets`, `note`. Unknown fields are ignored, so the data agent may add bookkeeping fields (for example `generated = "2026-11-20"`).

The scale of a spec's numbers is free (they need not be "per point of the main stat"), because every figure shown to the player is a ratio of two scores made with the same table. Keeping the main stat at 1.0 is still the convention: it makes tables readable.

## 2. Canonical stat keys

One unit of each key is what the weight multiplies. "Percent" keys are in **points of percent** (1 = 1%), never in rating.

| Key | Unit | Meaning |
|---|---|---|
| `STR` `AGI` `STA` `INT` `SPI` | 1 point | Primary stats |
| `ARMOR` | 1 armor | All armor on the item, base plus bonus (the game reports one sum) |
| `HEALTH` `MANA` | 1 point | Flat health or mana on the item (rare) |
| `AP` | 1 attack power | Melee attack power. Plain "attack power" also feeds `RAP` (see 3.3) |
| `RAP` | 1 attack power | Ranged attack power |
| `FERAL_AP` | 1 attack power | "Attack power in Cat, Bear... forms" on druid weapons |
| `SPELL_DMG` | 1 point | Spell damage, all schools |
| `HEAL` | 1 point | Healing |
| `SPELL_DMG_ARCANE` `SPELL_DMG_FIRE` `SPELL_DMG_FROST` `SPELL_DMG_HOLY` `SPELL_DMG_NATURE` `SPELL_DMG_SHADOW` | 1 point | One school's spell damage ("+Fire damage") |
| `HIT` `CRIT` | 1% | Melee and ranged hit and critical strike |
| `SPELL_HIT` `SPELL_CRIT` | 1% | Spell hit and critical strike |
| `HASTE` | 1% | Haste |
| `EXPERTISE` | 1% | Expertise (dodge and parry reduction) |
| `ARMOR_PEN` | 1% | Armor penetration |
| `DODGE` `PARRY` `BLOCK` | 1% | Avoidance chances |
| `BLOCK_VALUE` | 1 point | Damage a block stops |
| `DEFENSE` | 1 skill point | Defense skill |
| `MP5` `HP5` | 1 per 5 s | Mana and health regeneration |
| `SPELL_PEN` | 1 point | Spell penetration |
| `RES_FIRE` `RES_NATURE` `RES_FROST` `RES_SHADOW` `RES_ARCANE` | 1 point | Resistances (usually left out of weights) |
| `MH_DPS` | 1 damage per second | DPS of a weapon held in the main hand (one-hand, main-hand-only and two-hand weapons) |
| `OH_DPS` | 1 damage per second | DPS of a weapon held in the off hand |
| `RANGED_DPS` | 1 damage per second | DPS of a bow, gun, crossbow, thrown weapon or wand |
| `MH_SPEED` `OH_SPEED` `RANGED_SPEED` | 1 second | Swing time. **Reserved:** stage 1 has no language-free way to read speed (see 3.6), so these count as 0 until a later stage fills them. You may ship values now. |

Anything else in a `weights` table fails rule 5. The machine-readable list is `ns.Stats.KEYS` in `Stats.lua`.

## 3. How each key is read from the game

### 3.0 The sources

The engine calls `C_Item.GetItemStats(link)` (`DOC:ItemDocumentation.lua:1004-1018`; open, "may return nothing"). The generated docs do not list what the returned table holds. Two things do:

1. **The names.** The table's keys are the names of the game's own global strings ("A table whose fields are also globalstrings": the public wiki's page for the call, read 2026-11-20, which shows `ITEM_MOD_STAMINA_SHORT`, `ITEM_MOD_CRIT_RATING_SHORT`, `RESISTANCE0_NAME` and others). The complete set of such names on this client was read from its GlobalStrings database (`GAME:` file data ID 1394440): **234 names starting `ITEM_MOD_`**, `RESISTANCE0_NAME` to `RESISTANCE6_NAME`, and 23 starting `EMPTY_SOCKET_`. The English text stored beside each name says what the stat is ("Increases healing done by magical spells and effects by up to %s." is healing). The list, with those texts, is `Tools\tests\fixtures\client_stat_keys.txt`. One of the database's ten blocks is encrypted in the install and could not be read, so a name stored only there would be missing: `/gear debug` reports any name met in play that `Stats.lua` has no line for.
2. **The rating figures.** The client's combat ratings table (`GAME:` file data ID 1391669; `Tools\tests\fixtures\client_combat_ratings.txt`) has one row per level from 1 to 123 and one column per rating. **Every column holds a single value at every level**, so a rating converts the same at level 10 and at level 60. Second reference: the wowsims/forever simulator (MIT) uses the same figures (`Data\README.md`, "Which upstream repository").

`Stats.lua` accounts for every name on the client's list: it is either scored (section 3.1 to 3.4) or known and left out (section 3.5). `Tools\tests\test_stats.lua` reads the list and fails when a name is neither.

**The list is not everything the stat call can answer.** The first run in the game reported five names that are not on it: `ITEM_MOD_ARCANE_RESISTANCE_SHORT`, `ITEM_MOD_FIRE_RESISTANCE_SHORT`, `ITEM_MOD_FROST_RESISTANCE_SHORT`, `ITEM_MOD_NATURE_RESISTANCE_SHORT` and `ITEM_MOD_SHADOW_RESISTANCE_SHORT` (a few hundred sightings each, in the owner's `/gear debug` of 2026-11-20). They are scored now (section 3.1). Either they sit in the block of the string database that could not be read, or the engine answers names with no global string behind them. So the list is a floor, not a ceiling, and the unknown-name report of `/gear debug` is how the rest is found.

**A stat has two names.** Most stats exist twice in the client's list, once ending in `_SHORT` and once without (the short label and the long sentence of the same stat). The stat call usually answers the `_SHORT` name; for a healing bonus the bare name has been seen (`ITEM_MOD_SPELL_HEALING_DONE`). The engine therefore strips `ITEM_MOD_` and a trailing `_SHORT` and looks up what is left, the *stem*, so both names of every stat are read. The tables below give stems.

### 3.1 Plain stats (value copied)

| Stem (`ITEM_MOD_<stem>` and `ITEM_MOD_<stem>_SHORT`) | Canonical | The client's text |
|---|---|---|
| `STRENGTH` `AGILITY` `STAMINA` `INTELLECT` `SPIRIT` | `STR` `AGI` `STA` `INT` `SPI` | |
| `HEALTH` `MANA` | `HEALTH` `MANA` | |
| `POWER_REGEN0`, `MANA_REGENERATION` | `MP5` | "Mana Per 5 Sec.", "Restores %s mana per 5 sec." |
| `HEALTH_REGEN`, `HEALTH_REGENERATION` | `HP5` | "Health Per 5 Sec.", "Restores %s health per 5 sec." |
| `ATTACK_POWER` | `AP` and `RAP` (both) | "Increases attack power by %s." |
| `MELEE_ATTACK_POWER` | `AP` | "Melee Attack Power" |
| `RANGED_ATTACK_POWER` | `RAP` | "Increases ranged attack power by %s." |
| `FERAL_ATTACK_POWER` | `FERAL_AP` | "Increases attack power by %s in Cat, Bear, Dire Bear, and Moonkin forms only." |
| `SPELL_POWER` | `SPELL_DMG` and `HEAL` (both) | "Increases spell power by %s." |
| `SPELL_DAMAGE_DONE` | `SPELL_DMG` | "Increases damage done by magical spells and effects by up to %s." |
| `SPELL_HEALING_DONE` | `HEAL` | "Increases healing done by magical spells and effects by up to %s." |

| `BLOCK_VALUE` | `BLOCK_VALUE` | "Increases the block value of your shield by %s." |

| `ARCANE_RESISTANCE` `FIRE_RESISTANCE` `FROST_RESISTANCE` `NATURE_RESISTANCE` `SHADOW_RESISTANCE` | `RES_ARCANE` `RES_FIRE` `RES_FROST` `RES_NATURE` `RES_SHADOW` | (not on the client's readable list; seen in play, see 3.0. `HOLY_RESISTANCE` is left out.) |

Not `ITEM_MOD_` names:

| Name | Canonical | The client's text |
|---|---|---|
| `RESISTANCE0_NAME` | `ARMOR` | "Armor" |
| `RESISTANCE2_NAME` `RESISTANCE3_NAME` `RESISTANCE4_NAME` `RESISTANCE5_NAME` `RESISTANCE6_NAME` | `RES_FIRE` `RES_NATURE` `RES_FROST` `RES_SHADOW` `RES_ARCANE` | "Fire Resistance", "Nature Resistance", "Frost Resistance", "Shadow Resistance", "Arcane Resistance" |

Spell power, worked example: an item with 18 "damage and healing" and 6 more "damage" reports `SPELL_POWER = 18` and `SPELL_DAMAGE_DONE = 6`; the engine yields `SPELL_DMG = 24`, `HEAL = 18`. A damage caster weights `SPELL_DMG`, a healer weights `HEAL`, and neither double counts. (That an item lists the combined and the one-sided bonus as separate stats follows from the client having three separate names for them; a game check is listed.)

A school bonus is **not** folded into `SPELL_DMG`. A fire mage wants `SPELL_DMG = x` and `SPELL_DMG_FIRE = x` (or a share of x); a spec that leaves the school key out gets nothing from "+Fire damage" gear.

### 3.2 Ratings become percent

A rating is divided by the figure in the client's combat ratings table. The figure is the same at every level.

| Stem | Canonical | Rating per 1% | Column of the client's table |
|---|---|---|---|
| `CRIT_RATING` | `CRIT` and `SPELL_CRIT` | 14 | "Crit - Melee", "Crit - Ranged", "Crit - Spell" |
| `CRIT_MELEE_RATING`, `CRIT_RANGED_RATING` | `CRIT` | 14 | "Crit - Melee", "Crit - Ranged" |
| `CRIT_SPELL_RATING` | `SPELL_CRIT` | 14 | "Crit - Spell" |
| `HIT_RATING` | `HIT` and `SPELL_HIT` | 10 | "Hit - Melee", "Hit - Ranged", "Hit - Spell" |
| `HIT_MELEE_RATING`, `HIT_RANGED_RATING` | `HIT` | 10 | "Hit - Melee", "Hit - Ranged" |
| `HIT_SPELL_RATING` | `SPELL_HIT` | 10 | "Hit - Spell" |
| `HASTE_RATING` | `HASTE` | 10 | "Haste - Melee", "Haste - Ranged", "Haste - Spell" |
| `EXPERTISE_RATING` | `EXPERTISE` | 10 | "Expertise" |
| `ARMOR_PENETRATION_RATING` | `ARMOR_PEN` | 10 | "Armor Penetration" |
| `DODGE_RATING` | `DODGE` | 12 | "Dodge" |
| `PARRY_RATING` | `PARRY` | 15 | "Parry" |
| `BLOCK_RATING` | `BLOCK` | 5 | "Block" |
| `DEFENSE_SKILL_RATING` | `DEFENSE` (skill points) | 1 | "Defense Skill" |

Two things the data author must know:

- **A general hit or crit rating counts for spells too.** The client has four names for hit: the general one ("Increases your hit by %s.") and one each for melee, ranged and spell ("Improves melee hit by %s." and so on); the same for crit. The general rating moves all three, so the engine files it under the physical and the spell key. Second reference: wowsims/forever's stat code, where one hit or crit rating feeds melee, ranged and spells (`Data\README.md`). So "+1% hit" gear gives a caster `SPELL_HIT = 1` and a warrior `HIT = 1` from the same item. Give a caster spec `SPELL_HIT`/`SPELL_CRIT` weights and no `HIT`/`CRIT` weights (and the reverse for a physical spec), or the item is counted twice for that spec. A hybrid that truly benefits from both may weight both on purpose.

  How the shipped data files it, and what the engine does with it (checked by `test_data.lua`): at level 60, caster and healer specs weight only `SPELL_HIT`/`SPELL_CRIT`; melee, ranged and tank specs weight only `HIT`/`CRIT`. Retribution and Enhancement keep their one combined upstream weight under `HIT`/`CRIT`. Consequence: gear with a general "+1% hit" scores for every spec, while gear whose bonus is spell-only lands in `SPELL_HIT`/`SPELL_CRIT` alone and so scores 0 for Retribution and Enhancement, and melee-only bonuses score 0 for casters. That is intended. (Below 60 a few healer brackets, Holy Paladin among them, carry both `CRIT` and `SPELL_CRIT` weights on purpose: the bracket blends in the class's leveling profile, which swings a weapon. A general crit rating then counts on both sides for that bracket, as it does in play.)
- The division is exact for items whose tooltip says a whole percent (14 / 14 = 1). The engine does not round, so 7 rating reads as 0.5%.

The constants live in one table (`ns.Stats.RATING_PER_PERCENT`), and `test_stats.lua` compares each with the client's table.

### 3.3 Why general attack power feeds both `AP` and `RAP`

"Increases attack power by %s." raises melee and ranged attack power alike. What one such point is worth to a spec is therefore its `AP` weight **plus** its `RAP` weight, and that is how the engine counts it. A melee spec weights `AP` only. A hunter's table may hold both, a small melee share under `AP` and the large ranged share under `RAP`: that is not a double count, it is the two things the point does. (The shipped hunter tables do exactly this, 0.1 and 0.4.) A "ranged attack power" bonus goes to `RAP` alone.

### 3.4 Weapon damage

The stat call reports one number under the stem `DAMAGE_PER_SECOND` (the client's text: "damage per second"). The engine files it by the item's equip location (`itemEquipLoc`, 9th return of `C_Item.GetItemInfo`, `DOC:ItemDocumentation.lua:626-655`):

| Equip location | Canonical |
|---|---|
| `INVTYPE_2HWEAPON`, `INVTYPE_WEAPONMAINHAND`, `INVTYPE_WEAPON` | `MH_DPS` |
| `INVTYPE_WEAPONOFFHAND` | `OH_DPS` |
| `INVTYPE_RANGED`, `INVTYPE_RANGEDRIGHT`, `INVTYPE_THROWN` | `RANGED_DPS` |

A one-hand weapon (`INVTYPE_WEAPON`) is read as a main-hand weapon. For a character who can dual wield, `Compare.lua` also tries it in the off hand, counting the same damage with the `OH_DPS` weight in place of `MH_DPS`. So give dual-wield specs an `OH_DPS` weight.

A caster's wand is `RANGED_DPS`. Spell casters usually want no `MH_DPS` (leave it out).

Feral druids: on classic rules a form's damage ignores the weapon's DPS, and `FERAL_AP` carries a feral weapon's value. Whether this game version counts weapon DPS in forms, and whether a feral weapon's bonus arrives as `FERAL_ATTACK_POWER` or as `MELEE_ATTACK_POWER`, are game checks; the answers only change the weights of the two feral specs.

### 3.5 Known and left out

Every other name on the client's list is deliberately not scored. No weights table can name them, and `/gear debug` does not report them:

| Family | Stems | Why |
|---|---|---|
| Bonus armor | `EXTRA_ARMOR` | Taken to be inside the armor figure already (`RESISTANCE0_NAME` is all the item's armor); adding it would count it twice. Game check listed. |
| Holy resistance | `RESISTANCE1_NAME` | No gear decision turns on it. |
| School piercing, physical damage | `ARCANE_PENETRATION` ... `SHADOW_PENETRATION`, `PHYSICAL_DAMAGE_DONE` | Worth something only against one kind of target; no key. |
| Other powers' regeneration | `POWER_REGEN1` to `POWER_REGEN6` | Not mana. |
| Versus one creature type | `ATTACK_POWER_VS_*`, `SPELL_DAMAGE_VS_*` | Real under classic rules, but one number per spec cannot value them. |
| Weapon skills | `SWORDS`, `AXES`, `TWOHANDED_SWORDS`, `DAGGERS`, `DUAL_WIELD` and the rest | Worth something only with that weapon; no key in stage 1. |
| Taking fewer hits and crits, resilience | `HIT_TAKEN_*`, `CRIT_TAKEN_*`, `RESILIENCE_RATING`, `PVP_POWER`, `PVP_PRIMARY_STAT` | Not on this game's gear, or PvP only. |
| Not in this game's rules | `MASTERY_*`, `VERSATILITY`, `CORRUPTION*`, every `CR_*`, the "either attribute" stems (`AGILITY_OR_STRENGTH` ...) | Later expansions' stats. |
| Professions | `ALCHEMY` ... `TAILORING`, `FISHING`, `FIRST_AID`, `CRAFTING_SPEED`, `DEFTNESS`, `FINESSE`, `INGENUITY`, `INSPIRATION`, `MULTICRAFT`, `PERCEPTION`, `RESOURCEFULNESS`, `MODIFIED_CRAFTING_STAT_*` | Not combat stats. |
| Sockets | every `EMPTY_SOCKET_*` | No gems under this game's rules. |

### 3.6 Weapon speed

Not available from any documented call that is free of language: `C_Item.GetItemStats` has no speed name on the client's list, `C_Item.GetItemInfo` has no speed return (`DOC:ItemDocumentation.lua:638-655`), and a search of `DOC:ItemDocumentation.lua` and `DOC:TooltipInfo*.lua` for "speed" and "delay" finds nothing. The only place is the item tooltip's text line. The engine does not read tooltip text, so the stat record's `speed` is nil and the three `*_SPEED` weights multiply 0. The reader has a slot for it (`Game.ItemSpeed(link)`), so a later stage can fill it without changing the data format.

### 3.7 Rolled items ("... of the Bear"), and what a link's identity is

The engine always passes a full link. The link's identity (`Stats.Key`) keeps the item and its roll and drops everything else. The item string's fields, in the game's own order (the public wiki's ItemLink page, and the client's bug-report code which spells them out, `FX:Blizzard_PTRFeedback\Blizzard_Reports.lua:391`): 1 item, 2 enchant, 3-6 gems, 7 suffix, 8 unique ID, 9 link level, 10 specialization, 11 a mask no longer used, 12 item context, 13 the number of bonus IDs, then the bonus IDs, then the number of modifiers and (type, value) pairs, then relic and crafter fields.

- **Kept:** 1; 7 and 8 (an old-style random suffix and the number it scales by); the bonus IDs. On this client a roll travels as a bonus ID: the links the game itself wrote into saved variables read `item:7444::::::::33:1489:::1:12751::::::` ("of the Bandit" is bonus ID 12751 in fields 13-14, field 7 empty; 1,973 real links were looked at for the audit, none used field 7).
- **Dropped:** enchant and gems (not the item's own stats), link level and specialization (whoever made the link), the unused mask, the item context (where the item came from), and all modifiers (type 28, a content tuning number, differs by where the item dropped; type 9 is a timewalking level).
- The key is itself an item string (`"7444::::::::::::1:12751"`), so `"item:" .. key` is a link every game call takes; bonus IDs are sorted so one set gives one key.

Whether the stat call applies the roll for such a rebuilt link, with level and specialization blank, is a game check (`design\in-game-check.md`, step 5).

### 3.8 What changed when the tables were rebuilt from the client

| First draft | Rebuilt | Why |
|---|---|---|
| Only the `_SHORT` name of each stat was read | Both names of every stat | The client has both; a healing bonus arrives under the bare name (audit H1). |
| `ITEM_MOD_<SCHOOL>_SPELL_DAMAGE_DONE_SHORT` accepted beside `ITEM_MOD_<SCHOOL>_DAMAGE_DONE_SHORT` | Only `<SCHOOL>_DAMAGE_DONE` | The client has no name of the first spelling. |
| `ITEM_MOD_MELEE_ATTACK_POWER_SHORT` filed as `FERAL_AP` | Filed as `AP` | The client's text for it is "Melee Attack Power"; "Attack Power In Forms" is `FERAL_ATTACK_POWER`. Game check listed. |

| Weapon skill numbers with fist weapons under skill 473 | The client's character-sheet table: fist weapons under Unarmed, 162 | `FX:Blizzard_UIPanels_Game\Camelot\PaperDollFrameStats.lua:22-38`. |

## 4. Spec identity

### 4.1 The key

A spec is named `(class token, spec key)`, for example `("WARRIOR", "FURY")`. The spec key is our own English word from the weights file; it is never shown to the player raw (the display name comes from the game: `displayName` of the talent tree, section 4.2, or a localized text for variants).

### 4.2 Detecting it: talent trees, read through the trait system

This client plays by classic-era rules (three trees per class, no chosen specialization) but keeps talents in the modern trait system. The old talent-tab globals (`GetNumTalentTabs`, `GetTalentTabInfo`) do not exist: they have no entry in the generated docs and no caller in the client's UI. The client's own talent window reads the three trees like this, and so do we:

1. `C_SpecializationInfo.GetActiveSpecGroup()` gives the active build slot, 1 or 2 (`DOC:SpecializationInfoDocumentation.lua:41-56`; used at `FX:Blizzard_PlayerSpells\Camelot\ClassTalents\Blizzard_ClassTalentsFrame.lua:111-117`).
2. `C_SpecializationInfo.GetCombatConfigIDForSpecGroup(group)` gives that slot's config ID, or nil (`DOC:SpecializationInfoDocumentation.lua:90-104`; `FX:...\Blizzard_ClassTalentsFrame.lua:120`, `:183`).
3. `C_Traits.GetConfigInfo(configID).treeIDs[1]` gives the class's one tree (`DOC:SharedTraitsDocumentation.lua:201-215`).
4. `C_Traits.GetGroupDisplayInfoByTreeID(treeID)` lists the three groups, each `{ groupID, orderIndex, displayName, icon }` (`DOC:SharedTraitsDocumentation.lua:297-310`, struct `:1080-1091`; `FX:...\Blizzard_ClassTalentsFrame.lua:95-98`).
5. `C_Traits.GetGroupCurrencyInfo(configID, groupIDs)` gives each group's `currencyInfos[1].spent` (`DOC:SharedTraitsDocumentation.lua:281-295`; `FX:...\Blizzard_ClassTalentsFrame.lua:100-108`), matched by `traitNodeGroupID`, not by position (`FX:...\Blizzard_ClassTalentsFrame.lua:86-93`).

Each of the five calls is in the generated docs (the lines above) and is used this way by the client's own talent window (the `FX:` lines above): those are the two references.

Sorted by `orderIndex`, the groups' positions 1, 2, 3 are the `tab` numbers of this file. The data author should lay the tabs out in the classic left-to-right order:

| Class | tab 1 | tab 2 | tab 3 |
|---|---|---|---|
| WARRIOR | Arms | Fury | Protection |
| PALADIN | Holy | Protection | Retribution |
| HUNTER | Beast Mastery | Marksmanship | Survival |
| ROGUE | Assassination | Combat | Subtlety |
| PRIEST | Discipline | Holy | Shadow |
| SHAMAN | Elemental | Enhancement | Restoration |
| MAGE | Arcane | Fire | Frost |
| WARLOCK | Affliction | Demonology | Destruction |
| DRUID | Balance | Feral Combat | Restoration |

That this client orders the groups this way is **not verified offline** (the order comes from game data, not from Lua source). It is on the game check list; if a class differs, only the `tab` numbers in the data change.

None of the calls above carries a secret marker on its returns (their only annotation is `SecretArguments = "AllowedWhenUntainted"`), and none is a character-sheet stat call.

Not used: `C_SpecializationInfo.GetSpecialization()` / `GetSpecializationInfo()` (`DOC:SpecializationInfoDocumentation.lua:237-281`, which has a `pointsSpent` return). The client's character sheet only trusts them behind `IsSpecSelectionEnabled(classID)` (`FX:Blizzard_UIPanels_Game\Camelot\PaperDollFrame.lua:493-500`), which is for clients where a specialization is chosen; whether they answer anything useful here is not known and not needed.

### 4.3 The rule

- Auto = the tab with the most points spent. On a tie, the tab of the previous Auto answer keeps it when it is among the tied ones (no flapping while points are spent evenly); otherwise the lowest tab number of the tied ones.
- No points spent anywhere (below level 10, or just after a reset): the class's `default` spec.
- The player can pick any spec from `order` in the options page; that choice is saved per character and wins over Auto until set back to "Auto".
- Trait data is not ready in the first moments after login (`GetCombatConfigIDForSpecGroup` returns nil): the engine then uses the last Auto answer saved for the character, or `default`, and re-detects on `TRAIT_CONFIG_UPDATED` (`DOC:SharedTraitsDocumentation.lua:871-873`), `PLAYER_TALENT_UPDATE` and `ACTIVE_TALENT_GROUP_CHANGED` (`DOC:SpecializationInfoDocumentation.lua:503`, `:447`).

### 4.4 Variants

A tree with two play styles gets two spec keys on the same tab. Example:

```lua
DRUID = {
	default = "FERAL_CAT",
	order = { "BALANCE", "FERAL_CAT", "FERAL_BEAR", "RESTORATION" },
	specs = {
		BALANCE     = { tab = 1, role = "caster", ... },
		FERAL_CAT   = { tab = 2, role = "melee",  ... },                 -- Auto picks this for tab 2
		FERAL_BEAR  = { tab = 2, role = "tank",   manual = true, ... },  -- only by the player's choice
		RESTORATION = { tab = 3, role = "healer", ... },
	},
}
```

A variant needs a display name the game cannot supply. Add it to the list in section 8 so it gets a locale key; a tab's first spec in `order` needs none (it shows the game's tree name).

## 5. Level brackets

`weights` is the max-level table (level 60). `brackets` is an optional list, ascending by `upTo`. Each bracket covers the levels from one past the bracket before it up to its own `upTo`, and its `weights` are laid over the base table key by key (a key in the bracket replaces the base value; a key only in the base stays; to switch a stat off in a bracket write `KEY = 0`).

**The engine slides between brackets; it does not jump** (changed after the first data was in: the shipped tables differ so much from bracket to bracket, and most of all from 59 to 60, that advice would flip on a level-up). A bracket's table is taken to describe the **middle** of its span:

```
levels:   1 ......... 19 | 20 ........ 39 | 40 ........ 59 | 60
anchors:       10             29.5             49.5          60 (the base table)
```

- At or below the first anchor: the first bracket exactly as written.
- Between two anchors: each key moves in a straight line from one table to the other, `w = A + (B - A) x (level - levelA) / (levelB - levelA)`. A key missing on one side counts as 0 there.
- At level 60: the base table exactly as written.

So with `upTo = 19 / 39 / 59`, a level 10 character gets bracket 1, level 20 is about half way from bracket 1 to bracket 2, level 55 is about half way from bracket 3 to the level 60 table, and no single level-up moves a weight by more than one level's share. The code and its reasons are in `Spec.lua` (`Spec.Weights`); `Tools\tests\test_spec.lua` checks 19/20, 39/40 and 59/60 on a made-up table, and `test_data.lua` checks every shipped spec at every level.

What this means for the data author: write each bracket as "the right weights for the middle of this span", and the base as "the right weights at 60". Any number of brackets works; none is fine (the base then applies at every level).

## 6. What the data file does not hold

- Class proficiencies (which class can train which weapon and armor type): a small engine table in `Score.lua`, written by hand from common knowledge of classic rules (single source: a game check lists it); the weapon skill numbers beside it are the client's own (`FX:Blizzard_UIPanels_Game\Camelot\PaperDollFrameStats.lua:22-38`).
- Rating-per-percent constants: `Stats.lua` (section 3.2), from the client's table.
- Hit caps, talent adjustments, proc values: later stages, in files of their own.
- Display names, colors, icons: from the game at run time.

Every spec with `source = "wowsims"` must be covered by the MIT notice in `CREDITS.md` (the data agent owns that section). The engine never acts on `sourcePath` or `sourceCommit`; a debug command prints them.

## 8. Variant names

Every spec key that is not simply "the tree" needs an English display name (Title Case) and a locale key. In the code: `Spec.VARIANTS` (`Spec.lua`) and the `VARIANT` table in `Core.lua`; translated in all six language files.

| Class | Spec key | Display name |
|---|---|---|
| all nine | `LEVELING` | Leveling |
| DRUID | `FERAL_BEAR` | Bear |

A spec key listed here always shows this word, whatever its tab. Every other spec shows the game's own name of its talent tree (`displayName`), so `DRUID.FERAL_CAT` shows as the tree's name ("Feral Combat" on an English client).
